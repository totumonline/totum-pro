# Индексы

## <a name="pt-idx-task"></a> Задача

[Простые таблицы][88] и [таблицы циклов][89] хранят каждую строку в базе отдельно и годятся для сотен тысяч строк. Но `select` с `where` по полю без индекса читает всю таблицу: пока строк тысяча — незаметно, на сотне тысяч каждый такой запрос — секунды, а если он стоит в коде, который выполняется для многих строк, — минуты.

Индекс решает это для полей, по которым идет выборка. Но каждый индекс замедляет запись в таблицу и занимает место — индексы ставят осознанно, а не на все подряд.

## <a name="pt-idx-where"></a> Где нужны индексы

+ Только в простых таблицах и таблицах циклов. [Расчетные в цикле][1], `globcalcs` и [временные][34] таблицы хранятся целиком одной записью — индексы к ним не применяются.

+ На поля, которые стоят в `where` (и `order`) **частых или больших** выборок:

	+ колонки привязки подчиненных строк к владельцу (`product`, `client`, `order`) — по ним выбирают строки владельца;

	+ ключи, по которым ищут строку (`teh_key`, `fias_id`, `url`);

	+ хранимые поля для условий ([Кэш by design][729]) — ради них такие поля и заводят;

	+ флаги очередей фоновых расчетов (`update_filters_data = true`).

+ Не нужны на поля, которые только показываются, и на маленькие таблицы (справочники на десятки строк).

## <a name="pt-idx-types"></a> Какие индексы

+ **Обычный** — настройка таблицы [Индексы][115]: по индексу на каждое отмеченное поле. Для `where` по одному полю с одним значением или списком значений.

+ **Составной BTREE** — PRO, таблица `ttm__custom_indexes` ([Продвинутые индексы][685]): по нескольким полям сразу, когда выборка постоянно идет по ним вместе (`where: 'product' = …; where: 'obsolete' = false`) или с сортировкой по второму полю. Первым ставьте поле, которое есть во всех таких запросах.

+ **GIN** — PRO, там же: для поиска **значения внутри списка** — `where` по [множественному][195] [селекту][23] и по полю [Данные][38] со списком или `row` (в том числе [поиск по ключам в поле Данные][702]). Обычный индекс на такие условия не работает.

## <a name="pt-idx-measure"></a> Сколько индексов

**Не увлекайтесь индексами: ориентир — не больше одного индекса на 7–8 колонок строчной части.** Таблице из 20 колонок — два-три индекса на самые нагруженные выборки, а не по индексу на каждое поле из `where`.

+ Каждый индекс обновляется при каждой записи строки: таблица с десятком индексов пишется заметно медленнее, а в Totum запись — это и пересчеты, и коды действия.

+ Индекс на поле, где почти все значения одинаковые (`active` = `true` у 95% строк), почти не помогает — лучше составной индекс с полем, которое действительно сужает выборку.

+ Общие рекомендации по количеству — в разделе [Оптимизация][726].

## <a name="pt-idx-b2m"></a> B2M: логика расстановки

В B2M индексы пока стоят только на `b2m___cities` (`address`, `fias_id` — поиск города по адресу и ФИАС) и на служебных таблицах. Остальные таблицы ждут расстановки; рассуждение для них такое:

| Таблица | Выборки | Кандидат |
|---|---|---|
| `b2m___product_images`, `b2m___product_features`, `b2m___product_options`, `b2m___product_documents`, `b2m___reviews` | все строки товара: `where: 'product' = #id` в хранимых полях `b2m___items` и в коде действия таблицы | обычный индекс по `product` |
| `b2m___sku` | SKU товара: `where: 'product' = #id; where: 'obsolete' = false; where: 'base' = …` | составной BTREE `product`, `obsolete` |
| `b2m___items` | товары категорий: `where: 'all_categories' = $list` (значение внутри списка) | GIN по `all_categories` |
| `b2m___items` | поиск по характеристикам: `where: 'features_search' = {"ttm__filter": "jsonb", …}` | GIN по `features_search` |
| `b2m___catalog` | очередь демона: `where: 'update_filters_data' = true`; предки: `where: 'tree_children' = id` | на большом каталоге — GIN по `tree_children`; флаг — только если категорий тысячи |
| `b2m___stock` | движения SKU: `where: 'sku' = #id; where: 'final' = true` | составной BTREE `sku`, `final` |

## <a name="pt-idx-traps"></a> Ловушки

+ Создание индекса на большой таблице блокирует запись в нее на время построения — создавайте индексы в нерабочее время.

+ Индекс помогает `where` по самому полю. Условие, которое досчитывает значение в коде для каждой строки, индекс не ускорит — сначала сделайте [хранимое поле][729].

+ Прежде чем ставить индекс, найдите медленные запросы: лог отладки с выборками (`s`) показывает время каждого `select`, [профилирование][637] — нагрузку по таблицам и полям.
