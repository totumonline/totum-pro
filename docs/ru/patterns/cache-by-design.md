# Кэш by design: считать при записи, читать готовое

## <a name="pt-cache-task"></a> Задача

Данные системы пишутся редко, а читаются часто: товар правят раз в день, а выбирают его в каталоге, поиске, фильтрах и на витрине тысячи раз. Если производное значение (список всех категорий товара, остаток с учетом исключений, название с артикулом, набор ключей для поиска) считать **при чтении** — кодом, который собирает его из других полей и таблиц каждый раз, — платит каждая выборка. Большой `select` по таблице с сотнями тысяч строк, которому для условия нужно что-то досчитать, становится в разы тяжелее.

## <a name="pt-cache-principle"></a> Принцип

**Все, что можно посчитать в момент изменения и запомнить в поле, — считайте в действии и храните как значение.**

+ Пользователь не почувствует разницы, если его изменение сохранится за 0,2 секунды вместо 0,1.

+ Зато выборки, которые раньше досчитывали значение для каждой строки, начинают брать готовое поле, а по полю можно поставить [индекс][730] — большие `select` ускоряются в разы.

+ Цена — дисциплина записи: у каждого хранимого значения должен быть понятный «владелец», который обновляет его при каждом изменении источника.

Что стоит хранить:

+ **Значения для условий выборки** — то, что стоит в `where` больших `select`: нормализованные списки, ключи, флаги.

+ **Данные связанных строк**, которые нужны в каждой строке: одним `selectRow` в служебное поле — дальше остальные поля берут из него без запросов.

+ **Сводные значения** по подчиненным строкам: количества, суммы, остатки, статусы.

+ **Готовые структуры для витрины, API и поиска**: JSON карточки, индекс поиска, сгенерированный HTML.

## <a name="pt-cache-how"></a> Как хранить

| Способ | Когда пересчитывается | Для чего |
|---|---|---|
| [Код][27] поля в простой таблице / таблице циклов | при каждом пересчете строки | значение из полей **своей** строки — дешево, считается при изменении строки |
| Код с [только при добавлении][186] | при добавлении и по `reCalculate` с `field` | данные других таблиц — см. [Хранимые расчеты][711] и [Пересчет затронутых строк][712] |
| [Код действия][28] со `set` в поле | когда изменился источник | итог, который источник «проталкивает» владельцу сам |
| Фоновый расчет | демоном по флагу | тяжелые расчеты — см. [Тяжелые расчеты в фоне][714] |

## <a name="pt-cache-b2m"></a> Примеры из B2M

**Список категорий товара для `where`.** У товара основная категория и дополнительные. Поле `all_categories` таблицы `b2m___items` хранит их одним списком:

```totum
=: listAdd(list: json`[#main_category]`; list: #additional_categories)
```

А у категории каталога `b2m___catalog` хранится список всех ее потомков `tree_children` (см. [Деревья][734]). Товары категории со всеми подкатегориями выбираются одним запросом, без обхода дерева:

```totum
items_list: selectList(table: 'b2m___items'; field: 'id'; where: 'all_categories' = $list_add; where: 'active' = true)

	list_add: listAdd(list: #tree_children; item: #id)
```

Так считаются количество товаров категории, данные фильтров, цены «от» и «до» в категории.

**Данные связанной строки — одним запросом в служебное поле.** В `b2m___additional_items` поле `teh_data` берет нужные поля товара одним `selectRow`, остальные поля берут из него:

| Поле | Код |
|---|---|
| `teh_data` (Данные) | `=: selectRow(table: 'b2m___items'; field: 'product_image'; field: 'sku'; field: 'main_category'; where: 'id' = #product)` |
| `product_image` | `=: #teh_data[product_image]` |

**Сводные значения, которые проталкивает источник.** Остаток SKU с учетом исключенных складов (`with_exclude` в `b2m___sku`) записывается кодом действия при изменении остатка — а не считается в каждом месте, где он нужен. Наличие товара (`in_stock` в `b2m___items`) записывает SKU, когда меняется наличие.

**Готовое для витрины и поиска.** `catalog_prices`, `features_data`, `all_catalog_data` в `b2m___items` — готовый JSON для страниц каталога; `ttm_search` — готовая строка индекса поиска; HTML меню, фильтров и главной страницы генерируется в файлы при изменении данных, а витрина отдает готовые файлы.

## <a name="pt-cache-traps"></a> Ловушки

+ **Каждый писатель источника должен обновлять кэш.** Перечислите все места, которые меняют источник (поля, кнопки, коды действия, API, импорт), и убедитесь, что каждое запускает пересчет. Найти их помогает поиск по кодам.

+ Не кэшируйте то, что меняется чаще, чем читается (счетчики просмотров, «последняя активность»): запись станет дороже выигрыша.

+ Хранимое поле, по которому идут выборки, — кандидат на [индекс][730]; поле для `where` по значению внутри списка (`all_categories`) — на GIN-индекс.

+ Пересчет кэша у многих строк — в одном действии (`setList`, `reCalculate` с `where` по списку), а не построчно — см. [Массовые изменения и общий триггер][735].
