# Нагрузка: отслеживание изменений и демоны

## <a name="pt-load-actual-task"></a> Задача

[Актуальность][104] таблицы — проверка, не изменил ли ее кто-то другой, пока шло действие. Если изменил, транзакция перезапускается, а пользователи получают уведомление «таблица изменена». Для обычных таблиц это защищает данные. Но в таблицах, куда одновременно пишут многие, отслеживание превращается в нагрузку: постоянные перезапуски транзакций, блокировки на записи кода изменения, поток уведомлений.

## <a name="pt-load-actual-where"></a> Где снижать отслеживание

+ **Таблицы циклов, в которых работают несколько человек.** Даже если каждый работает в своем цикле, они сталкиваются на самой таблице циклов: изменение внутри цикла автоматически пересчитывает строку цикла — это запись в общую таблицу циклов. Для них — **«! PRO Без отслеживания с уведомлениями»**: перезапусков нет, а уведомление об изменении пользователи видят.

+ **Таблицы, в которые пишут внешние системы** (несколько remotes, вебхуки, API, импорт) и фоновые процессы: логи, очереди, журналы событий. Для них — **«!! PRO Полностью деактивирован»** ([off][683]): нет проверки, нет записи кода изменения, нет уведомлений — только быстрая запись.

+ Для отдельного действия в обычной таблице — параметры [exclude и silent][682] функций изменения, без смены режима всей таблицы ([Тяжелые расчеты в фоне][714]).

В B2M:

| Таблица | Режим | Почему |
|---|---|---|
| `b2m___customers` (покупатели, циклы) | ! PRO Без отслеживания с уведомлениями | покупатели и менеджеры работают в своих циклах одновременно |
| `b2m___orders` (заказы, циклы) | ! PRO Без отслеживания с автообновлением | заказы приходят с витрины постоянно, менеджеру нужен актуальный список |
| `auth_log`, `notifications`, `b2m___vk_states_and_code_v` | ! Без отслеживания изменений | служебные записи при входе и уведомлениях |

> В таблице без отслеживания данные **хедера** могут быть невалидными: держите в хедере таких таблиц только кнопки ([Актуальность][104]).

## <a name="pt-load-daemons"></a> Демоны: осторожно

Демон ([Daemons][649]) — процесс, который крутится постоянно и может запускаться с интервалом меньше секунды. Ошибка в нем бьет по всей системе, а не по одному пользователю:

+ тяжелый код активации с интервалом в доли секунды — постоянная нагрузка на базу, даже когда работы нет;

+ код демона, который не снимает флаг или падает с ошибкой на одной и той же строке, будет брать ее снова и снова — без пауз;

+ несколько нагруженных демонов на сервере с одним-двумя ядрами займут процессор целиком.

На слабом сервере такой демон кладет систему. Поэтому:

+ код активации — один дешевый `select` (по флагу, по настройке включения), `activation_interval` — секунды, а не доли;

+ за запуск — одна порция работы, `pause` между порциями;

+ новый демон сначала проверяется кнопкой `do_it_now`, и только потом активируется; у демона должен быть выключатель (настройка, по которой код активации возвращает `false`, — в B2M «Автогенерация фильтров каталога»);

+ следите за ошибками демона после включения.

Подробно о том, как строить очередь для демона, — [Тяжелые расчеты в фоне][714].
