# Кастомные интерфейсы

PRO. Собственный интерфейс поверх Totum: свои страницы (сайт, личный кабинет, рабочее место оператора, мобильная форма), которые работают на данных, авторизации, ролях и лицензии Totum, но выглядят и ведут себя как нужно вам.

Решение сначала собирается обычными средствами Totum — таблицами, кодами, ролями — и полностью работает в стандартном интерфейсе. Затем к нему подключается кастомный интерфейс: страницы на PHP / HTML / JS, которые показывают и меняют те же данные. Дальнейшие изменения делаются в двух местах: в логике Totum и в интерфейсе, который ее использует.

## <a name="ci-how"></a> Как это работает

+ Интерфейсы описываются в таблице циклов `ttm__interfaces` (дерево: Системные таблицы → PRO Разное → Кастомные интерфейсы). Одна строка (цикл) — один интерфейс; его настройки и пути — в таблице цикла `ttm__interface` (Настройки кастомного интерфейса).
+ Страницы интерфейса — PHP-шаблоны в папке `interfaces/<name интерфейса>/` в корне установки Totum (рядом с `Conf.php`): `/home/totum/totum-pro/interfaces/<name>/`.
+ Для каждого запроса Totum сначала проверяет пути включенных интерфейсов. Если адрес подходит под путь — отдается шаблон этого пути, иначе запрос обрабатывается как обычно (таблицы, авторизация, API и т.д.).
+ Шаблон выполняется от имени текущего пользователя Totum, внутри транзакции: в нем доступны объект Totum, пользователь и конфигурация.

## <a name="ci-enable"></a> Включение

Кастомные интерфейсы выключены по умолчанию. Включаются в `Conf.php` в корне установки — добавьте в класс `Conf` свойство:

```php
protected $interfacesSwitchedOn = true;
```

Без него таблица `ttm__interfaces` ни на что не влияет.

## <a name="ci-settings"></a> Настройки интерфейса

Добавьте строку в `ttm__interfaces` и откройте цикл. Хедер таблицы `ttm__interface`:

| Поле | name | Назначение |
|---|---|---|
| Название | `h_name` | name интерфейса: имя папки шаблонов `interfaces/<name>/` и, для неосновного интерфейса, первый сегмент адреса `/<name>/…` |
| Статус | `h_status` | интерфейс включен |
| Основной | `h_main` | основной интерфейс — работает от корня сайта `/`, а не от `/<name>/`. Основной интерфейс должен быть один |
| Webuser | `h_webuser` | открывать страницы без авторизации от имени системного пользователя `webuser` — см. [Авторизация][694] |
| Путь авторизации | `h_auth_path` | куда перенаправлять неавторизованного пользователя со страниц, которые требуют авторизации. Если пуст — `/`. Указывается адрес на этом же сайте, без хоста |
| Шаблон 404 | `h_template_404` | шаблон страницы «не найдено» основного интерфейса |

Значения хедера показываются в строке интерфейса в `ttm__interfaces` (`name`, `main`, `webuser`, `status`, `auth_path`, `template_404`), пути — в `paths`.

### <a name="ci-paths"></a> Пути

Строчная часть `ttm__interface` — пути интерфейса. Каждая строка связывает адрес с шаблоном:

| Поле | name | Назначение |
|---|---|---|
| Имя пути | `path_name` | название для себя, на работу не влияет |
| Regexp | `regexp` | `path_regexp` — регулярное выражение, а не точный адрес |
| Секция | `section` | префикс адреса: путь проверяется только для адресов, начинающихся с `/<section>`, и сравнивается с остатком адреса после него |
| Regexp пути | `path_regexp` | адрес страницы (`/`, `/catalog`) или регулярное выражение |
| Название шаблона | `template_name` | имя файла шаблона в папке `interfaces/<name>/`, например `index.php` |
| Авторизация | `auth` | страница только для авторизованных пользователей |

#### <a name="ci-paths-match"></a> Как адрес сопоставляется с путями

**С чем сравнивается `path_regexp`.** Неосновной интерфейс живет по адресам `/<name>/…`: первый сегмент адреса — это `name` интерфейса, а в `path_regexp` пишется только то, что идет **после** него. Основной интерфейс живет от корня сайта, и в `path_regexp` пишется адрес целиком.

Например, неосновной интерфейс `cabinet` и основной интерфейс:

| Адрес в браузере | Неосновной `cabinet`: с чем сравнивается | Основной: с чем сравнивается |
|---|---|---|
| `/cabinet` | `/` | `/cabinet` |
| `/cabinet/orders` | `/orders` | `/cabinet/orders` |
| `/cabinet/orders/15` | `/orders/15` | `/cabinet/orders/15` |
| `/orders` | — (не начинается с `/cabinet`, интерфейс не проверяется) | `/orders` |

То есть страница `/cabinet/orders` неосновного интерфейса `cabinet` — это путь с `path_regexp` = `/orders`, а не `/cabinet/orders`.

**Секция.** Если у пути заполнено `section`, путь проверяется только для адресов, которые начинаются с `/<section>`, и этот префикс тоже отрезается. Путь с `section` = `orders` и `path_regexp` = `/15` в интерфейсе `cabinet` сработает на адрес `/cabinet/orders/15`. Секцией удобно группировать пути одного раздела.

> Префикс секции проверяется без границы слова: секция `shop` подойдет и для `/shopping`. Если это мешает, используйте пути с regexp.

**Порядок проверки:**

1. Адрес `/` (корень сайта) — у основного интерфейса берется путь с `path_regexp` = `/`.
2. Точные пути (`regexp` выключен): адрес после отрезания `/<name>` и `section` должен совпасть с `path_regexp` полностью.
3. Пути с `regexp`: `path_regexp` ищется в адресе как регулярное выражение (`~…~`). Выражение не привязано к началу и концу строки — для точного совпадения пишите `^…$`, например `^/orders/\d+$`.
4. Внутри каждой группы пути проверяются в порядке строк таблицы; берется первый подходящий.

> У основного интерфейса адрес сравнивается вместе с GET-параметрами: точный путь `/catalog` не совпадет с `/catalog?page=2` — для страниц с параметрами используйте regexp `^/catalog(\?|$)`.

Если ни один путь не подошел — адрес обрабатывается стандартными модулями Totum. Если и модуля с таким именем нет — показывается `Шаблон 404` основного интерфейса.

> Основной интерфейс занимает корень сайта, но стандартный интерфейс Totum остается доступен по своим адресам: `/Table/…`, `/totum`, `/Auth/…` — если пути интерфейса их не перекрывают. Не делайте путей основного интерфейса, которые совпадают с этими адресами.

## <a name="ci-auth"></a> Авторизация

Авторизация общая с Totum: та же сессия и та же cookie, что у стандартного интерфейса (страница входа `/Auth/Login`, [OpenID][695], [LDAP][617], [2FA][634]). Пользователь, вошедший в Totum, авторизован и в интерфейсе, и наоборот.

Для неавторизованного пользователя:

+ путь с `auth` — перенаправление на `Путь авторизации` интерфейса (или `/`);
+ иначе, если включен `Webuser`, — страница выполняется от имени системного пользователя с логином `webuser`. Его нужно создать в таблице пользователей самостоятельно и выдать ему роли с доступом только к тому, что можно видеть без входа;
+ иначе — перенаправление на страницу входа Totum `/Auth/Login/?from=<адрес>`.

Права в интерфейсе — права пользователя Totum: его роли определяют доступ к таблицам и полям.

## <a name="ci-templates"></a> Шаблоны

Шаблон — PHP-файл `interfaces/<name>/<template_name>`. Он подключается внутри контроллера интерфейса, поэтому в нем доступны:

+ `$this->Totum` — объект Totum текущего пользователя: `$this->Totum->getTable('name')` — таблица, выборки, расчеты;
+ `$this->User` — текущий пользователь (`getId()`, `getRoles()`, `isCreator()`, `getTables()` — доступные таблицы);
+ `$this->Config` — конфигурация схемы (`getSettings('…')` — значения таблицы Настройки);
+ `$this->interface` — данные интерфейса и пути: `['interface' => <строка ttm__interfaces>, 'template' => <шаблон>, 'auth' => <auth пути>]`;
+ `$settings` — `h_title`, `h_og_title`, `h_og_description`, `h_og_image` из таблицы Настройки (для `<title>` и OpenGraph).

Шаблон выполняется в транзакции: контроллер подтверждает ее после того, как шаблон отработал; при конфликте одновременного доступа выполнение повторяется (до 5 раз). Если шаблон завершается `exit` / `die`, до подтверждения дело не доходит — см. [ниже][697].

Пример реального интерфейса на этой схеме — интернет-магазин [totum-b2m-ru](https://github.com/totumonline/totum-b2m-ru/tree/b2m/interfaces/b2m): шаблоны страниц, GET- и POST-эндпойнты, статика в `public/`.

### <a name="ci-totum-code"></a> Рекомендуемая схема: шаблон выполняет код Totum

Делайте PHP-шаблон тонкой оберткой, а саму страницу — HTML, json, логику — собирайте **кодом Totum**:

+ коды страниц хранятся в таблице Totum: строка — шаблон, поле с кодом (`text/totum`) и уникальный ключ вида `<name интерфейса>--<шаблон>` (`shop--catalog`, `shop--product`);
+ PHP-шаблон собирает переменные запроса (адрес, GET / POST, имя интерфейса), находит код страницы по ключу, выполняет его и выводит результат.

Так вся логика и разметка редактируются в Totum, работают все функции кодов, а PHP-файлы почти не меняются. Один PHP-шаблон может обслуживать несколько страниц, выбирая ключ кода по адресу.

Пример `interfaces/shop/catalog.php`. Таблица кодов — `shop_templates` с полями `interface_key` (ключ) и `template_code` (код):

```php
<?php
use totum\common\calculates\Calculate;

$url = '/' . trim(parse_url($_SERVER['REQUEST_URI'] ?? '/', PHP_URL_PATH) ?? '', '/');
$interface_name = basename(__DIR__); // имя папки шаблонов = name интерфейса

$Vars = ['url' => $url, 'get' => $_GET, 'interface_name' => $interface_name]; // в коде — $#url, $#get, $#interface_name
$Table = $this->Totum->getTable('shop_templates'); // таблица-контекст кода: #поля и $#ntn ссылаются на нее

$CA = new Calculate("=: exec(code: @shop_templates.template_code.interface_key['{$interface_name}--catalog']; var: 'url' = $#url; var: 'get' = $#get; var: 'interface_name' = $#interface_name)");
$result = $CA->exec(['name' => 'exec'], [], [], [], $Table->getTbl(), $Table->getTbl(), $Table, $Vars);

echo $result;
```

+ Код выполняется через [exec][286]: `@shop_templates.template_code.interface_key['shop--catalog']` — [короткое обращение][217] к коду по ключу, переменные передаются в него через `var:`.
+ Таблица-контекст нужна для выполнения кода. Ее хедер загружается целиком — возьмите таблицу без тяжелого хедера, например саму таблицу кодов.
+ В коде страницы доступны обычные переменные кода, в том числе `$#nu` — id текущего пользователя.

Код страницы возвращает готовую строку HTML (или [ассоциативный массив][30] для json-ответа), например:

```totum
=: str`"<h1>Каталог</h1><ul>" + $items + "</ul>"`

items: listJoin(list: $li; str: "")
li: selectList(table: 'products'; field: 'html_li'; where: 'published' = true; order: 'title' asc)
```

**Код или код действия.** `Calculate` выполняет код как [Код][27] — для чтения и расчетов. Если страница или эндпойнт меняет данные или вызывает функции действий (`set`, `insert`, `emailSend`, `notificationSend` …), выполняйте его как [Код действия][28] — `CalculateAction`:

```php
$CA = new \totum\common\calculates\CalculateAction($totum_code);
$result = $CA->execAction('exec', [], [], $Table->getTbl(), $Table->getTbl(), $Table, 'exec', $Vars);
```

### <a name="ci-endpoints"></a> Эндпойнты для запросов из JS

Данные, которые страница подгружает из JS (`fetch`), удобно отдавать отдельными путями интерфейса — эндпойнтами. Например, путь с regexp `^/get-endpoints/` ведет на шаблон `get_endpoints.php`, путь `^/post-endpoints/` — на `post_endpoints.php`. Шаблон эндпойнтов:

+ берет имя эндпойнта из адреса (`/get-endpoints/getCart` → `getCart`) и ищет его в **белом списке** — массиве `имя => ключ кода, тип ответа (json / string), тип выполнения (код / код действия)`. Неизвестное имя — ответ 404;
+ для POST-эндпойнтов проверяет метод запроса (`$_SERVER['REQUEST_METHOD'] === 'POST'`) — иначе 405: данные форм (пароли и т.п.) не должны попадать в адрес и логи;
+ выполняет код и отдает ответ: для json — `header('Content-Type: application/json; charset=utf-8')` и `json_encode($result, JSON_UNESCAPED_UNICODE)`, для строки — `echo $result`.

<a name="ci-exit"></a>Если после ответа шаблон завершает работу через `exit`, контроллер уже не подтвердит транзакцию — изменения кода действия откатятся. Подтверждайте и откатывайте ее сами:

```php
try {
    $CA = new \totum\common\calculates\CalculateAction($totum_code);
    $result = $CA->execAction('exec', [], [], $Table->getTbl(), $Table->getTbl(), $Table, 'exec', $Vars);
    $this->Totum->transactionCommit(); // exit ниже не дойдет до подтверждения контроллером
} catch (\Exception $e) {
    $this->Totum->transactionRollback();
    http_response_code(400);
    echo $e->getMessage();
    exit;
}

header('Content-Type: application/json; charset=utf-8');
echo json_encode($result, JSON_UNESCAPED_UNICODE);
exit;
```

### <a name="ci-guards"></a> Проверка входных данных

Шаблон получает адрес и параметры запроса напрямую от браузера — проверяйте их до выполнения кода:

+ адрес — по белому списку символов, например `^[a-z0-9/-]+$`; все остальное — на страницу 404;
+ длину ключей и значений GET / POST — слишком длинные отбрасывайте (в b2m это отдельные `get_guard.php` и `post_guard.php`, которые подключаются в начале каждого шаблона);
+ ip посетителя берите только из `$_SERVER['REMOTE_ADDR']`: заголовки `X-Real-IP` / `X-Forwarded-For`, если их не проставляет ваш прокси, может прислать сам клиент с любым значением.

Страница «не найдено»: код страницы возвращает строку, начинающуюся с `404`, а шаблон в этом случае перенаправляет на `/404`; шаблон пути `/404` выполняет свой код и отдает `http_response_code(404)` до вывода тела.

### <a name="ci-rights"></a> Права доступа в шаблоне

Шаблон выполняется от имени текущего пользователя, но **права его ролей к данным, которые шаблон берет сам, не применяются**. Коды Totum (`select`, `selectRowList` …) и выборки из PHP (`getByParams`) возвращают все строки и все поля таблицы, независимо от того, кто открыл страницу. Доступ к таблице, видимость полей и префильтры Totum проверяет только тогда, когда пользователь работает с таблицей через ее страницу `/Table/…` (в том числе запросами из JS — см. [Работа с данными из браузера][696]).

Поэтому то, что страница показывает пользователю, ограничивайте сами:

+ в коде страницы — условиями выборки по текущему пользователю: `where: 'client' = $#nu`;
+ в PHP — проверкой доступа к таблице `$this->User->getTables()` ([ассоциативный массив][30] `id таблицы => доступ`) и строк — `checkIsUserCanViewIds('web', $ids, isCritical: 'FILTER')`: из переданных id возвращает только видимые пользователю в web (с учетом ролей и [префильтров][48]);
+ выводите только те поля, которые можно показывать этому пользователю.

Данные, которые выводятся в HTML, экранируйте: иначе текст, введенный пользователями в поля Totum, выполнится на странице как HTML / JavaScript. В PHP — `htmlspecialchars($value)`, в коде Totum — заменой `<`, `>`, `&`, `"` через [strReplace][241].

### <a name="ci-static"></a> Статические файлы

Статические файлы интерфейса (JS, CSS, картинки) должны отдаваться nginx напрямую, а nginx отдает только папку `http/` установки. Рекомендуем хранить статику вместе с интерфейсом, в отдельной подпапке без PHP-файлов, и сделать на нее символическую ссылку `http/interfaces/<домен>`:

```
mkdir -p /home/totum/totum-pro/http/interfaces
ln -s /home/totum/totum-pro/interfaces/shop/public /home/totum/totum-pro/http/interfaces/shop.example.com
```

Файлы будут доступны по адресам `/interfaces/<домен>/…`, например `/interfaces/shop.example.com/css/shop.css`.

+ Папка по домену разделяет статику схем, если одна установка Totum обслуживает несколько доменов: у каждого домена своя ссылка.
+ Существующие файлы nginx отдает сам, до маршрутизации интерфейсов, поэтому адреса `/interfaces/…` пути интерфейсов не перехватывают.
+ Не делайте ссылку на всю папку интерфейса `interfaces/<name>/`: тогда PHP-шаблоны станут доступны по прямому адресу, и nginx выполнит их отдельно, в обход контроллера интерфейса и проверки авторизации.

### <a name="ci-error"></a> Шаблон ошибки

Если при выполнении шаблона возникло исключение, транзакция отменяется и подключается файл `interfaces/<name>/error` (без расширения). В нем текст ошибки — в переменной `$error` (уже экранирован), создателю к тексту добавляется путь ошибки в кодах. Тот же шаблон показывается при ошибках кодов Totum, вызванных из шаблона.

Свои ошибки в шаблоне (нет доступа, не найден объект, неверные параметры) выбрасывайте как `errorException` Totum — тогда пользователь увидит шаблон ошибки, а все изменения данных, сделанные шаблоном до ошибки, будут отменены:

```php
<?php
use totum\common\errorException;

$id = (int)($_GET['id'] ?? 0);
if (!$id) {
    throw new errorException('Не указан заказ');
}
```

+ Для страниц не завершайте работу через `die` / `exit` при ошибке: шаблон ошибки не покажется, а транзакция не будет подтверждена. Если ответ — не страница, а текст или json для JS (эндпойнты), ошибку удобнее перехватить и отдать текстом с кодом ответа — тогда откатите транзакцию сами, см. [Эндпойнты][697].
+ Ошибка кода Totum, выполняемого из шаблона, — тоже исключение: если его не перехватывать, пользователь увидит шаблон ошибки с ее текстом.
+ Ошибки PHP (`TypeError`, обращение к методу у `null` и т.п.) — это не исключения (`\Exception`), шаблон ошибки на них не срабатывает: пользователь получит ошибку PHP. Проверяйте данные и выбрасывайте `errorException` сами.
+ Шаблон выводит HTML сразу по ходу выполнения. Если ошибка случится в середине страницы, шаблон ошибки выведется после уже отданной части. Поэтому все выборки и проверки делайте в начале шаблона, до вывода HTML — как в примерах выше.

Пример `interfaces/<name>/error`:

```php
<!DOCTYPE html>
<html>
<head><title>Ошибка</title></head>
<body>
<div class="error"><?= $error ?></div>
<a href="/">На главную</a>
</body>
</html>
```

### <a name="ci-front"></a> Работа с данными из браузера

Страница интерфейса может работать с данными Totum и из JS — теми же запросами, что и стандартный интерфейс. Адреса таблиц (`/Table/<раздел>/<id таблицы>`, для таблиц в цикле — `/Table/<раздел>/<id таблицы циклов>/<цикл>/<id таблицы>`) являются эндпойнтами ядра: действия (получить данные, изменить поле, нажать кнопку, добавить строку …) вызываются POST-запросом по адресу таблицы с параметром `method`. Запрос идет с cookie сессии, права проверяются как в web. Методы — в `totum/moduls/Table/ReadTableActions.php` (чтение) и `WriteTableActions.php` (изменение).

Для интеграции с отдельным фронтендом удобнее [PRO JSON API][391] — у него стабильный формат запросов и ответов.
